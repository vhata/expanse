## Summary

The gates are green and the CLI's happy paths work. The problems are in three places. First, the daemon: it keeps a long-lived copy of the store and writes it back, which loses snippets added elsewhere and replaces a malformed store, and its menu is never actually rebuilt because rumps' `menu` setter only adds items. Second, the storage boundary: `expanse/core.py` checks only that the store parses and has an `expansions` key, so other malformed shapes, non-string values and I/O errors end in tracebacks, and `load_expansions` turns a parse error into an empty store, which leaves protecting the file to each caller. Third, the Hammerspoon contract (`dump` and `get`) has no test, and names containing newlines break it. Most of the packaging, install-helper and documentation drift was already in `TODO.md`; this review confirms that those entries still hold and adds detail to three of them.

## Invariants

Carried from `ARCHITECTURE.md`, all holding at `87b0e01`:

- All file access to the snippet store goes through `expanse/core.py`.
- The location of the store comes from `$HOME`; tests never touch the real `~/.expanserc`.
- `expanse/core.py` and `expanse/cli.py` import nothing macOS-specific.

Added by this review. The code needs these properties and does not enforce them yet; the findings that violate each are named:

- A store that fails validation is never written by any writer. Only the CLI enforces this, by calling `ensure_expfile` first (`load-swallows-malformed-store`, `daemon-saves-over-malformed-store`).
- Every writer reads the store immediately before it writes, so no writer holds a stale copy (`daemon-saves-stale-store`).
- Every name is a single line and every value is a string. The two-line `dump` format and the `get` output depend on this (`dump-name-newline-breaks-pairs`, `store-shape-unvalidated`, `get-prints-non-string-values`, `edit-abort-stores-null`).

## Findings

### Open and Moved

#### Bug

- `daemon-saves-stale-store` — **The daemon overwrites snippets added by the CLI after it started.** Bug · Open · Verified.
  - Where: `expanse/daemon.py:13` (`ExpanseDaemon.__init__`) loads once; `expanse/daemon.py:117-119` (`save_expansions`) writes the in-memory copy.
  - Severity: P2. This is silent data loss, but only while the optional daemon is running.
  - Reproduced headlessly with a temporary `HOME`: construct `ExpanseDaemon`, run `expanse add -n fromcli -e y`, then add a snippet through the daemon and save. The store ends as `{"a": "1", "fromdaemon": "z"}` and `fromcli` is gone. Fix: reload before every mutation.
  - Queued as TODO `daemon-reloads-store`.
- `daemon-saves-over-malformed-store` — **One daemon edit replaces a store it could not parse.** Bug · Open · Verified.
  - Where: `expanse/daemon.py:13`, `expanse/daemon.py:118`; `expanse/core.py:20-21` (`load_expansions`).
  - Severity: P2.
  - Reproduced with a temporary `HOME` containing `{"expansions": {"keep": "me"},`: one daemon add and save leaves `{"expansions": {"new": "x"}}`. The snippet `keep` is gone. The daemon never calls `ensure_expfile`.
  - Queued as TODO `daemon-guards-malformed-store`.
- `daemon-menu-not-rebuilt` — **After a change, the daemon's menu keeps deleted snippets and appends new ones below the management items.** Bug · Open · Verified.
  - Where: `expanse/daemon.py:59`, `:94`, `:115` (`self.menu = self.build_menu()`); rumps 0.4.0's `App.menu` setter calls `Menu.update`, which ignores existing keys.
  - Severity: P2.
  - Reproduced headlessly with store `{a, b}`: delete `a`, add `c` and reassign the menu. The keys become `a, b, sep, Add, Edit, Delete, c, sep`, and invoking `copy_expansion` for `a` raises `KeyError: 'a'`. Fix: clear the menu (`self.menu.clear()`) before rebuilding it.
- `daemon-menu-title-collision` — **A snippet named like a management item cannot be copied from the daemon.** Bug · Open · Verified.
  - Where: `expanse/daemon.py:18-23` (`build_menu`); menu keys are titles.
  - Severity: P3.
  - With a store holding a snippet named `Add Expansion`, the menu has one `Add Expansion` item and its callback is `add_expansion`. The snippet is unreachable. `Edit Expansion`, `Delete Expansion` and rumps' `Quit` collide the same way. Fix: put the snippets in a submenu or prefix the management titles.
- `edit-abort-stores-null` — **Quitting the editor without saving stores `null`, after which `dump` crashes.** Bug · Open · Verified.
  - Where: `expanse/cli.py:33-34` (`edit`).
  - Severity: P2. A crashing `dump` empties the Hammerspoon chooser.
  - `HOME=$(mktemp -d) EDITOR=true expanse edit -n z` leaves `{"expansions": {"z": null}}`, and `expanse dump` then raises `AttributeError: 'NoneType' object has no attribute 'replace'` (status 1).
  - Queued as TODO `edit-abort-keeps-content`.
- `store-shape-unvalidated` — **`ensure_expfile` reports only two kinds of malformed store; every other kind either passes validation or ends in a traceback.** Bug · Open · Verified.
  - Where: `expanse/core.py:34-42` (`ensure_expfile`), `expanse/core.py:13-21` (`load_expansions`).
  - Severity: P3. The file was left unchanged in every case.
  - Each case below was run against a temporary `HOME`:
    - A store of `[]` makes every command fail with `TypeError`.
    - `{"expansions": []}` passes `ensure_expfile`, and then `add` fails with `TypeError` and `dump` with `AttributeError`.
    - `{"expansions": {"a": 1}}` passes, and `dump` fails with `AttributeError`.
    - Invalid UTF-8 raises `UnicodeDecodeError`, a directory raises `IsADirectoryError`, and mode 000 raises `PermissionError`, each as a traceback rather than the "Could not access expansion file" message.
  - Fix: validate the whole shape (a dict of string to string) and catch `OSError` and `ValueError` in one place.
- `get-prints-non-string-values` — **For a non-string value, `get` prints its Python repr, and Hammerspoon copies that.** Bug · Open · Verified.
  - Where: `expanse/cli.py:114` (`get`).
  - Severity: P3.
  - With a store of `{"n": null, "i": 3}`, `expanse get -- n i` prints `None` and `3` and exits 0, so the chooser silently copies the text `None`. This is the `get` side of `edit-abort-stores-null`, and it applies to any hand-edited non-string value.
- `dump-name-newline-breaks-pairs` — **A snippet name containing a newline shifts every later entry in the Hammerspoon chooser.** Bug · Open · Verified.
  - Where: `expanse/cli.py:122-124` (`dump`) escapes newlines in content only; `expanse/cli.py:41-55` (`add`) accepts any name. `~/.hammerspoon/expanse.lua:75` pairs lines two at a time.
  - Severity: P3.
  - After `expanse add -n $'a\nb' -e one` and `add -n c -e two`, `dump` prints the five lines `a`, `b`, `one`, `c`, `two`. The independent agent ran the Lua parser against that output: names and contents swap from the bad entry onwards, and the last snippet is dropped. Fix: reject names containing newlines in `add` and `edit`, and state the rule under Shared interfaces in `ARCHITECTURE.md`.
- `add-stdin-strips-whitespace` — **`add` without `-e` strips leading indentation from the snippet.** Bug · Open · Verified.
  - Where: `expanse/cli.py:54` (`add`), `.strip()`.
  - Severity: P3.
  - Piping `    indented\n` into `expanse add -n i` stores `"indented"`. Content given with `-e` is stored unstripped, so the two input paths disagree. Fix: remove only the single trailing newline.
- `daemon-entry-points-broken` — **`run.sh` and `python -m expanse.daemon` do not start the daemon.** Bug · Open · Read.
  - Where: `run.sh:7`; `expanse/daemon.py:122-124` has no `__main__` guard.
  - Severity: P3.
  - Still as the TODO entry describes. In addition, `run.sh` is tracked as mode 100644, so `./run.sh` (suggested in `CLAUDE.md`) fails with "permission denied" before it reaches the import error.
  - Queued as TODO `fix-daemon-entry-points`.
- `daemon-install-missing-script` — **`install.sh` and `com.expanse.daemon.plist` install `expanse_daemon.py`, which does not exist.** Bug · Open · Read.
  - Where: `install.sh:7-10`, `com.expanse.daemon.plist:9`.
  - Severity: P3.
  - Still holds. With `KeepAlive` set, launchd would keep retrying the missing path. `install.sh:4` also installs with `pip3` into the global interpreter.
  - Queued as TODO `fix-daemon-install`.

#### Design

- `load-swallows-malformed-store` — **`load_expansions` returns an empty store when parsing fails, so each caller has to remember to validate first.** Design · Open · Verified.
  - Where: `expanse/core.py:17-21`; the `KeyError` in its `except` is unreachable, because `json.load` does not raise it.
  - Severity: P2. This is the root cause of `daemon-saves-over-malformed-store`.
  - The CLI is safe only because the group callback calls `ensure_expfile` first (`expanse/cli.py:16`). Any new caller that skips that call repeats the daemon bug. Fix: make `load_expansions` raise a store error, and let `ensure_expfile` reuse that same validation, which also removes the double read.
- `store-world-readable` — **The store is created mode 0644, so other local accounts can read every snippet.** Security · Open · Verified.
  - Where: `expanse/core.py:27` (`save_expansions`), `expanse/core.py:45` (`ensure_expfile`); both use `Path.open("w")` under the default umask.
  - Severity: P3. Snippets can hold credentials.
  - A new store was created as `-rw-r--r--`. The home directory on this machine is `drwxr-x---` with group `staff`, which every standard macOS account belongs to. Fix: create the file with mode 0600, which fits the temporary-file-and-replace write that `atomic-save` already plans.
- `save-not-atomic` — **An interrupted save can truncate the store.** Design · Open · Read.
  - Where: `expanse/core.py:26-28` (`save_expansions`).
  - Severity: P2.
  - Still holds: the store is opened with mode `w` and written in place.
  - Queued as TODO `atomic-save`.
